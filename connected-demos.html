Review context and source decisions

Storyboard draft · 24 September 2026. The sequences below are proposed demonstrations, not results from a configured customer org. Names, records, thresholds and messages are illustrative fixtures. Screenshot briefs describe captures to make during rehearsal; they are not manufactured product screens. MuleSoft is outside this collection.

The Agentforce workshop makes it possible to demonstrate an actual customer task: verify a customer, inspect the agent user's access, make a narrowly permitted change, and examine the evidence. The guardrail notes and Ryan deck add the surrounding lifecycle: configure the agent, constrain its actions, inspect its execution, and improve its tests. Their general architecture statements need to be separated from capabilities proven in a particular channel and release.

The new material changes three important demo choices. First, an identified customer does not automatically become the Salesforce user executing an agent action. Second, the workshop's export policy is a volume rule, not a sensitive-field rule. Third, the workshop's Prompt Builder masking demonstration must remain separate from Agentforce execution: current Salesforce documentation says that masking is disabled for agents, including prompt templates invoked through agent actions. Vignette 01 8–10 minutes planned

Control a sensitive report export

Who can export customer data, who actually exported it, and what prevents an inappropriate export?

A service analyst legitimately needs a contact report. The same report can also include a sensitive field that should not leave Salesforce through ordinary report export.

Storyboard

Connected controls
Security Center exposes permission grants → Event Monitoring establishes activity → classification identifies the fields requiring protection → a configured Transaction Security Policy acts on a supported report event.

How Guardian contributes
The customer can connect entitlement, observed use and enforcement around the same user and report. Classification is an input to the policy design; it does not activate a policy by itself.

7 frames · Each capture brief names the evidence to collect during rehearsal.

01. Show who has the capability

Screen: Security Center, Who Sees What Explorer, System Permissions lens; inspect the export permission and its users.

Do: Find the demo analyst, Avery Chen, in the results. Open the assignment provenance. If the org has a corresponding Security Insights finding, begin there and use Who Sees What for the user-level explanation.

Presenter

“This tells us who has the ability to export. It does not tell us who has used it.”

Evidence: A real permission result and the profile or permission set contributing it. Record the actual count at capture time; no prewritten estate-wide statistic.

Screenshot brief

v01-01-export-permission.png — permission name, Avery's row and assignment source. Exclude unrelated users.

02. Establish what this user did

Screen: The org's prebuilt Event Monitoring Analytics or Event Log Object analytics dashboard, where it exposes the selected event; otherwise a prepared query/report for the supported report-export event.

Do: Locate Avery's rehearsed export by user, report and timestamp. Point to the fields actually present in the captured event. Keep the report identifier visible across the next frames.

Presenter

“Here is an observed export by the same person. Permission exposure and activity are different questions.”

Evidence: A stored event from the rehearsed operation. Use the actual event schema; do not promise a CSV payload, every cell value, or an outcome field that the selected event does not contain.

Screenshot brief

v01-02-export-activity.png — user, event time, report identifier and available operation/row-count details.

03. Identify the sensitive column

Screen: Security Center Data Classification and the report definition.

Do: Show the demo sensitive field's metadata classification, then the field in the report. Use a field with synthetic values and a verified API-name mapping. Keep a second report with the same row count and no sensitive column.

Presenter

“We want the decision to depend on the sensitivity of the exported columns, not simply on the size of the report.”

Evidence: The selected field's classification and the report column referencing it. Classifications must already be synchronised to the metadata used by the policy.

Screenshot brief

v01-03-classified-column.png — field API name, classification and matching report column; a labelled two-panel capture is acceptable.

04. Show the enforcement rule

Screen: Transaction Security policy and its reviewed condition implementation.

Do: Explain the custom Apex condition prepared for this demo: for the supported export operation, resolve the report event's column identifiers to field metadata and match the agreed sensitivity category. Use the policy's supported block action. Document handling of unresolved identifiers and approved exceptions.

Presenter

“This policy connects the classified field to a report-export decision. The connection is configured and tested; a label alone does not block an export.”

Evidence: The active policy, action and tested classification lookup. This storyboard specifies the policy contract; it does not supply a production-ready Apex class.

Screenshot brief

v01-04-sensitive-export-policy.png — policy event, activation state and action, with a short explanation of the custom condition beside it.

05. Allow the ordinary report

Screen: Avery's user session and the report without the sensitive column.

Do: Export the ordinary report. Use the same supported UI route that will be used for the sensitive report. Keep the row count equal in both fixtures so volume cannot explain the different outcomes.

Presenter

“The ordinary service task still works.”

Evidence: The permitted export completes. Check that another policy, such as a default step-up rule, does not obscure the intended result during rehearsal.

Screenshot brief

v01-05-ordinary-export.png — report context and the completed operation, with synthetic output only.

06. Block the sensitive report

Screen: Avery's session and the report containing the classified column.

Do: Attempt the export. Show the actual configured block message and verify that this attempt did not produce a file.

Presenter

“This person can use reports, but this export crosses the boundary we configured.”

Evidence: A policy-specific block, not a missing object permission or a browser download failure. Preserve the corresponding notification or policy evidence available in the org.

Screenshot brief

v01-06-sensitive-export-blocked.png — report name and real block message in one view.

07. Close the investigation loop

Screen: The rehearsed event and policy notification, with the original permission result available alongside them.

Do: Connect permission, activity and policy result using the user, report and time. Explain how excess export assignments could now be removed separately from the runtime guardrail.

Presenter

“We can reduce unnecessary access and still protect the legitimate people who retain it.”

Evidence: A small evidence bundle from this rehearsal. If report contents must be proven later, preserve the permitted output at the time under the agreed handling process; Field Audit Trail is not a historical report snapshot.

Screenshot brief

v01-07-export-evidence.png — three labelled observations, each identifying its real source. A presenter-created summary is labelled as such.

Setup and rehearsal
  • Enable the required user-level permission view in Who Sees What. Prepare Avery, two equal-size reports and one supported field with synthetic sensitive values. Confirm object, field and record access first; the demo should fail at the export policy, not an earlier permission check.
  • Enable the required Real-Time Event Monitoring storage and/or streaming paths before generating events. Prepare the analytics/query view and allow for ingestion. Event Log Objects are stored, queryable data; they are not a synonym for the streaming channel.
  • Implement and review the custom Apex classification condition. Test API-name resolution for the selected report type and handling of missing metadata. Joined reports, aliases, calculated columns and alternative export routes require their own tests; do not imply coverage from this single report.
  • The TSP Accelerator from Salesforce Labs can help with relevant policy examples. Inspect what a chosen template actually implements; do not describe a row-count template as classification-aware.
  • Minimum rehearsal cases: ordinary report allowed; classified report blocked; changing only the classification changes the expected rule match after the configured refresh; an unsupported or unresolved column follows the explicitly chosen policy behaviour.
  • If the custom condition is not ready, demonstrate the workshop's RowsProcessed > 100 and export-operation policy as a volume-based fallback. Rename the vignette segment accordingly and omit any claim that classification caused the block.
  • Restore Avery's assignments and the demo classification after rehearsal. Keep the baseline screenshots and events dated so a later permission snapshot is not mistaken for the earlier state.
Sources and implementation notes

Source basis: The user's requested export story; the security journey's Access and Monitor sections; the workshop's Data Classification and Event Monitoring exercises; Shield second-call setup guidance.

Verified product connections: Who Sees What Explorer supports inspection of system permissions and their users. Salesforce describes classification-based export control using custom Apex in its data-classification article. The current ReportEvent policy reference lists supported condition fields and actions; do not infer a native sensitivity condition from the workshop's row-count example.

Build boundary: Custom condition code and its tests are required for the primary version. The policy only covers the selected supported event and route. It is not a universal Salesforce DLP engine covering every API, screenshot or agent response.

Journey connections: Security 01 Foundation, 03 Access, 04 Monitor. Sharing 02 Permissions, 05 Other access paths, 07 Maintain access.

Vignette 02 7–9 minutes planned

Remove excess access and detect its return

Why can an employee see a sensitive record, and what will tell us if broad access is assigned again?

A service user should work on standard regional cases but has acquired a broad system permission through an old permission set.

Storyboard

Connected controls
Inspect effective access → remove the excess grant → test the intended sharing boundary → monitor new high-risk assignments.

How Guardian contributes
Who Sees What helps explain the current grants. Security Center alerts provide an ongoing signal when selected powerful permissions are assigned again. The actual access correction remains a Salesforce permission and sharing change.

7 frames · Each capture brief names the evidence to collect during rehearsal.

01. State the intended access

Screen: A simple requirements card and three synthetic records.

Do: Introduce Taylor, an East-region service user. Use a supported custom object, Policy__c, with an East standard record, an East confidential record and a West standard record. The agreed task permits only the East standard record.

Presenter

“We will test one clear business boundary, not redesign the whole organisation during the demonstration.”

Evidence: A three-row expected-access table. These are illustrative records, not a claim about a real customer's model.

Screenshot brief

v02-01-access-intent.png — user, three records and expected allow/deny results.

02. Explain the unexpected visibility

Screen: Who Sees What Explorer, Taylor's effective permissions and assignment sources.

Do: Identify the prepared broad grant, such as View All Data, and its contributing permission set. Inspect the relevant object and record context. Show the extra visible record in Taylor's own session.

Presenter

“The sharing rule is not necessarily the problem. A separate broad grant can explain why this person sees more than the intended model.”

Evidence: Actual grant provenance plus the user-session result. Do not infer an exact access reason merely from seeing a high-risk permission count.

Screenshot brief

v02-02-excess-grant.png — selected permission, source and user identity.

03. Remove the source of the grant

Screen: Permission assignments; then Who Sees What comparison or refreshed user view.

Do: Remove the obsolete assignment. Retain an appropriate minimum profile and the task-specific permission sets. Check for the same permission through other assignments before declaring it removed.

Presenter

“Permissions accumulate. Removing one source is sufficient only if another source does not still grant the same capability.”

Evidence: The effective permission is absent after the relevant refresh; Taylor can still open the required application and object.

Screenshot brief

v02-03-permission-corrected.png — before/after effective permission result, labelled with capture times.

04. Test sharing and the restriction

Screen: The custom object's private OWD, regional sharing rule and applicable restriction rule; Taylor's session.

Do: Show the regional grant and the rule excluding confidential records for the selected service-user population. Test the three fixture records through the supported UI and a rehearsed API route using Taylor's identity.

Presenter

“The share grants regional access. The restriction narrows the supported record set further.”

Evidence: East standard allowed; West standard and East confidential denied in the tested routes. Record the specific object and user criteria; do not generalise restriction-rule support to all objects or elevated users.

Screenshot brief

v02-04-record-boundary.png — concise actual results with the applicable configuration.

05. Explain where muting fits

Screen: An optional, separately prepared permission set group example.

Do: Show a group that includes an unnecessary object Delete permission, with that permission muted within the group. Inspect whether Taylor receives Delete from another source before testing.

Presenter

“Muting removes this group's contribution. It does not deny a permission granted by Taylor's profile or another assignment.”

Evidence: A group-level result and the full effective-permission result. Keep this optional frame out of the executive path if it distracts from the record-access story.

Screenshot brief

v02-05-muting-scope.png — group contribution and effective result, explicitly distinguished.

06. Prepare and demonstrate a drift alert

Screen: Security Center alert configuration for a selected high-risk permission, then its rehearsed notification.

Do: Configure the alert for the prepared broad permission. In a disposable demo user, reassign the monitored permission and capture the notification after the normal processing cycle.

Presenter

“We corrected the current access. Now there is a signal when this selected powerful permission is assigned again.”

Evidence: The configured condition, affected user and actual resulting alert. Do not promise instant delivery or detection of every possible sharing change.

Screenshot brief

v02-06-permission-drift.png — alert rule and real notification, with timestamps.

07. Recheck the boundary

Screen: The original three-record test and refreshed effective permissions.

Do: Remove the demonstration drift, repeat the record tests and show the access model still supports the legitimate task. Record the alert's owner in the demo runbook, without turning that ownership into a product capability.

Presenter

“The result is a tested access boundary with a continuing check for the high-risk grant we chose to monitor.”

Evidence: Corrected permissions and the allow/deny matrix. Retain both successful work and prohibited-access tests.

Screenshot brief

v02-07-access-rechecked.png — final access matrix and permission result.

Setup and rehearsal
  • Build this story in a sandbox with a supported custom object. Verify restriction-rule eligibility, user criteria, record criteria and bypass behaviour against the target release. Do not use an administrator as the restricted test user.
  • Configure the intended minimum permissions before the meeting. Ensure the demonstration can be reset without rebuilding a customer's sharing model.
  • Use Who Sees What for effective-access inspection, and the actual user session for behavioural proof. A dashboard count alone is not an access test.
  • Muting is optional. Use a permission such as object Delete with understood dependencies; keep a separate grant available only if demonstrating why muting is not a global deny.
  • Create the high-risk assignment alert and its recipient configuration before rehearsal. Allow snapshot or processing delays, and date the notification.
  • Minimum tests: permitted task succeeds; both prohibited records remain inaccessible; the high-risk assignment is detected; removing it restores the intended boundary. Reset the broad grant immediately after capture.
Sources and implementation notes

Source basis: The sharing journey's additive-permission model, OWD, restriction rules and maintenance steps. The demonstration's East/West records and rule are proposed fixtures, not a supplied customer configuration.

Verified Guardian functions: Who Sees What Explorer and Security Insights alert configuration. The latter supports alerts for selected high-risk system-permission assignments to users or permission containers.

Build boundary: Native Salesforce permissions and sharing enforce access. Security Center exposes and monitors the configuration; it does not replace the sharing model. The alert shown here is not a claim that every OWD, sharing, field-permission and guest-access change generates the same alert.

Journey connections: Security 03 Access, 07 Governance. Sharing 02 Permissions, 03 Defaults, 04 Sharing, 05 Restrictions, 06 Test, 07 Maintain access.

Vignette 03 8–10 minutes planned

Investigate a suspicious Salesforce session

Which Salesforce activity becomes more concerning when identity and endpoint context are added?

An employee's Salesforce activity initially looks like ordinary work. The security team wants to know whether the associated identity and device context justify a closer investigation.

Storyboard

Connected controls
Observe Salesforce activity → add connected identity and endpoint signals → evaluate a configured correlation → investigate and choose a response.

How Guardian contributes
Event Monitoring provides Salesforce activity. Threat Detection provides supported anomaly signals. Security Mesh can bring connected sources into a common investigation context. A correlation and a response workflow must be configured; enrichment alone does not block an action.

7 frames · Each capture brief names the evidence to collect during rehearsal.

01. Start with the Salesforce activity

Screen: A prepared Event Monitoring view of a synthetic user's login and subsequent supported activity.

Do: Select Jordan's recorded session window. Show the available user, time, application and network context. Identify a report export or another supported event captured during that window.

Presenter

“The Salesforce event tells us what happened here. We need more context before deciding how suspicious it is.”

Evidence: Real captured events. Where no common session key is available, label a user-and-time match as an investigation hypothesis rather than a proven session join.

Screenshot brief

v03-01-salesforce-activity.png — the two relevant events and their available identifiers.

02. Show a supported anomaly signal

Screen: A rehearsed Threat Detection event or a Security Mesh impossible-travel finding.

Do: Choose one supported signal that exists in the demo environment. Show its time and explanation, then open the underlying evidence. Use a clearly labelled replay if the signal cannot be generated predictably during the meeting.

Presenter

“This is a detection to investigate. It is not proof that the employee was compromised.”

Evidence: An actual finding, not a hand-drawn product alert. Do not promise that a scripted pair of logins will reliably trigger a machine-learning detector on demand.

Screenshot brief

v03-02-anomaly-signal.png — detection type, evidence and time range.

03. Add the external context

Screen: Security Mesh's connected-source data or the prepared investigation view.

Do: Show the matching Okta ISPM user information and CrowdStrike endpoint evidence actually ingested. Identify the joining attributes and the freshness of each record.

Presenter

“We are checking the identity and endpoint context associated with this activity. The evidence is useful only if the identities and times line up.”

Evidence: Connected records with a defensible mapping. Do not describe an Okta ISPM user feed as a complete Okta authentication-event stream.

Screenshot brief

v03-03-identity-endpoint-context.png — source names, timestamps and the mapped identity/device attributes.

04. Show the configured correlation

Screen: The custom detection or investigation rule built for this vignette.

Do: Explain the proposed rule: flag the rehearsed export when available endpoint-risk evidence and the Salesforce identity match within the configured time window. Show the matching records and any exclusions.

Presenter

“This rule combines the sources for this use case. We are showing a configured correlation, not claiming that every cross-tool scenario is prebuilt.”

Evidence: The real rule output and its source references. If device-to-user mapping is unavailable, narrow the story to the identity correlation that can actually be demonstrated.

Screenshot brief

v03-04-correlated-finding.png — the real finding and its contributing records.

05. Explain the remaining uncertainty

Screen: The finding detail alongside the investigation timeline.

Do: Compare event occurrence time with ingestion time. Check whether the device was shared, the network was a VPN or the identity mapping is stale.

Presenter

“The combined evidence helps prioritise investigation. We still need to validate context before treating the activity as malicious.”

Evidence: A short investigator annotation identifying confirmed facts and unresolved assumptions. Label this annotation as the team's interpretation.

Screenshot brief

v03-05-investigation-context.png — timeline with source and analyst annotations separated.

06. Show a deliberate response

Screen: A prepared response record and the appropriate supported Salesforce or identity-administration control.

Do: Demonstrate the chosen action on the disposable account, such as revoking the relevant session through a supported administrative path. Show a reauthentication or denied-session result in the test session.

Presenter

“Detection informs this response. The administrator or the configured response workflow performs it.”

Evidence: An actual response and its observed effect. A Transaction Security Policy is a separate control on a supported event; do not imply this finding automatically invokes any arbitrary policy.

Screenshot brief

v03-06-session-response.png — response record and observable session result.

07. Describe the SIEM handoff accurately

Screen: The receiving SIEM record, only if that outbound integration has been built and rehearsed; otherwise the source finding and a labelled handoff specification.

Do: Show the correlated finding's source references and context preserved at the destination. Identify the configured export/API mechanism used by the implementation.

Presenter

“The destination can receive an enriched finding through this configured handoff. It is separate from collecting raw Salesforce events.”

Evidence: A real delivered record if demonstrated. Without a delivery path, stop at the Security Mesh investigation and retain SIEM forwarding as an implementation item.

Screenshot brief

v03-07-investigation-handoff.png — actual destination record, or a clearly labelled proposed field mapping. No MuleSoft dependency.

Setup and rehearsal
  • Prepare Security Center with the required Data 360 configuration, supported connectors and a suitable ingestion history. Use synthetic or approved demonstration telemetry; never manufacture a finding inside an authentic-looking screenshot.
  • Pick a repeatable recorded detection. Threat Detection's statistical behaviour is unsuitable for a promise that an alert will fire at a precise second in front of an audience.
  • Build the custom correlation and validate identity, endpoint and timestamp joins. Specify how shared devices, missing values, clock offsets and stale records affect the match.
  • Rehearse a clean control case with normal context so the investigation view does not imply every export is suspicious.
  • Confirm which response is manual and which is automated. If automation is included, show its separately configured trigger and action; no generic claim of automatic cross-product remediation.
  • The SIEM frame is optional and requires a working outbound integration. If absent, omit the frame from the presentation instead of claiming a native automatic feed.
  • Restore the disposable user's session and account state after the demonstration. Keep the recorded telemetry timestamps visible.
Sources and implementation notes

Source basis: Security journey 04 Monitor and 07 Governance; the user's request for Okta/CrowdStrike correlation; Guardian's estate-wide posture story.

Verified connection: Salesforce's September 2026 Security Mesh explanation describes RTEM, Okta ISPM and CrowdStrike signals, OCSF normalisation, an impossible-travel detection and a foundation for custom detections. That supports the investigation design, not a claim that this exact exfiltration correlation or outbound SIEM integration is preconfigured.

Build boundary: Connectors, identity mapping and the custom detection are implementation work. The response and outbound handoff are separate. A finding is evidence for investigation, not a conclusive attribution of an attack.

Journey connections: Security 02 Authentication, 04 Monitor, 07 Governance. Sharing 05 Other access paths, 07 Maintain access.

Vignette 04 10–12 minutes planned

Let a verified customer update only their own details

Can the agent update this customer's phone number without updating somebody else's record?

Maria Gomez asks a service agent to change her contact phone number. The agent must verify Maria, use the verified identity in its action, and have only the Salesforce access necessary for that task.

Storyboard

Connected controls
Customer verification → deterministic action eligibility → customer-scoped backend operation → object, field and record permissions → recorded change and execution evidence.

How Guardian contributes
Who Sees What makes the agent user's permissions inspectable. Field Audit Trail extends the configured field-history evidence. Agentforce's verification and action controls are complementary platform capabilities; they are not features supplied by Shield.

8 frames · Each capture brief names the evidence to collect during rehearsal.

01. Identify the execution user

Screen: The prepared Merchant Support Agent's access settings, followed by Who Sees What for its actual user.

Do: Show which Salesforce user executes this service-agent configuration. Identify Contact access and the contribution granting Phone read access. Check object and record access too.

Presenter

“Maria is the customer in the conversation. This configuration executes through a dedicated agent user. These are two different identities.”

Evidence: The actual agent-user mapping and effective permissions. This story deliberately uses the workshop's dedicated-user service-agent model; it is not a claim about every Agentforce channel.

Screenshot brief

v04-01-agent-execution-user.png — agent name, execution user and Contact.Phone permission source.

02. Attempt the private task before verification

Screen: A fresh customer conversation.

Do: Ask, “Please update my phone number to 214-555-7776.” Show that the prepared private action is unavailable until verification succeeds. Inspect the deterministic condition in the builder.

Presenter

“The instruction to verify the customer is backed by an action gate. The model does not decide whether to skip it.”

Evidence: No Contact change and no successful update action in the trace. Do not use a polite refusal alone as proof of enforcement.

Screenshot brief

v04-02-verification-required.png — conversation response, gate and unchanged record evidence.

03. Establish the verified customer identity

Screen: The controlled verification flow and resulting trusted session state.

Do: Use Maria's synthetic email identity and the configured verification process. Complete it through a controlled test inbox. Show that the successful backend result sets the verified customer identifier.

Presenter

“The verification result supplies the customer identifier used by the next action. A name typed into chat is not enough.”

Evidence: Verification succeeds for Maria and produces the expected identifier. Keep codes, tokens and secrets out of screenshots. An emailed code here is customer verification; do not describe it as phishing-resistant MFA.

v04-03-customer-verified.png — verification state and a non-sensitive identifier alias, with the secret omitted.

04. Show the customer-scoped action

Screen: The action's Flow or Apex implementation and its configured inputs.

Do: Explain how it uses the trusted verified identifier to select Maria's record. Show the server-side check that refuses an arbitrary Contact ID supplied in conversation. Review the action's execution context and its CRUD/FLS/sharing enforcement.

Presenter

“The agent user may serve many customers. This action still has to bind the request to the verified customer's record.”

Evidence: The actual implemented check, not just an action description or prompt. Variables representing verification must not be freely writable by the customer or inferred from their assertion that they are verified.

Screenshot brief

v04-04-customer-scoped-action.png — gate, trusted input mapping and backend record-selection check.

05. Demonstrate the field-permission boundary

Screen: The verified conversation and Who Sees What.

Do: In the prepared read-only baseline, attempt the phone update and inspect the permission failure. Add the narrowly approved Phone edit grant, leaving the rest of the task's permissions unchanged. Refresh the access inspection and repeat.

Presenter

“Being verified does not grant Salesforce permissions. The action also needs the specific field access approved for this task.”

Evidence: Read-only attempt does not change Phone; the narrowly corrected configuration permits the update. Object Edit and access to the record must already be verified; FLS alone is not sufficient.

Screenshot brief

v04-05-phone-permission.png — baseline failure, exact grant and effective-access result. Use dated before/after panels.

06. Test the prohibited request

Screen: The same verified conversation, followed by the two fixture Contact records.

Do: Ask to update a different customer's phone, then try to change a separate protected field for which the action has no approved capability. Keep those records and fields deliberately outside the action contract.

Presenter

“The legitimate change works. Verification does not let Maria select somebody else's record or expand the action to other fields.”

Evidence: Maria's approved Phone change succeeds; the other customer's record and protected field remain unchanged. The trace identifies the rejection or absence of the forbidden action.

v04-06-cross-customer-denied.png — request, actual result and unchanged target record.

07. Show what changed and how it happened

Screen: The tracked Phone history and the associated agent session trace.

Do: Show old value, new value, time and recorded Salesforce user for the configured tracked field. Separately show the action execution in the agent trace. Use available identifiers, record and time to connect the evidence.

Presenter

“The history shows the field change. The session trace shows the agent execution around it. Together they support the investigation.”

Evidence: Actual records from rehearsal. Do not promise a native agent-session identifier in every Field Audit Trail row. If the join is manual, call it a manual correlation and preserve the trace reference in the case notes.

v04-07-agent-change-evidence.png — history row and trace, with the correlation method labelled.

08. Show the narrow result

Screen: A compact outcome card with links or references to the captured evidence.

Do: Summarise four observed outcomes: unverified request blocked; verified own-record update permitted; other-customer update refused; change evidence retained.

Presenter

“The agent can complete the customer's task within a defined identity, action and data boundary.”

Evidence: Each outcome points to the rehearsal capture that proves it. Do not replace the tests with an architecture diagram alone.

v04-08-agent-outcomes.png — four-row presenter summary, labelled as a demonstration summary.

Setup and rehearsal

Setup and rehearsal
  • Agree the fixture's treatment criteria with the relevant data owner for a real deployment. The demonstration uses synthetic cohorts and makes no jurisdiction-specific legal-retention claim.
  • Select and document the exact Archive implementation. Current Salesforce Help explicitly distinguishes the Archive managed package covered by the legal-hold article from Salesforce Archive; features and interfaces must not be blended.
  • Configure Privacy Center's selected records and related-data scope. The workshop's three-year example is an illustrative filter, not a universal retention rule. Do not automatically delete field history merely because that option appears in an exercise.
  • Rehearse archive retrieval using an authorised user and a user expected to be denied. Include the archived view and any direct retrieval path actually used by the audience.
  • Coordinate hold exclusions across the live-data policy and the archive workflow. A held record in one store does not establish a cross-product policy integration.
  • Rehearse deletion only on a disposable synthetic fixture. Capture the preview/selection and final job result. Do not rely on the backup story to imply that a deliberately irreversible privacy treatment should be casually undone.
  • Build the copy inventory in advance. Record the scope of any backup privacy request and the treatment of logs, files and history separately; avoid a promise that one job erases all copies.

Screenshot capture guidance

Every frame has a stable filename. Capture only the decisive screens for the meeting; the full list is a storyboard production checklist, not a requirement to show every image in one presentation.

  • Capture the authentic product interface in the configured demo org. Do not redraw a product result to make the intended story look successful.
  • Preserve the product/feature identity and enough surrounding context to understand the result. Crop unrelated names, tenant identifiers, secrets and notification recipients.
  • Keep key identifiers consistent across a story. If sanitising an identifier, apply the same substitution in every frame and label the screenshots as sanitised.
  • Use the real timestamps. Clearly distinguish recorded rehearsals, current live actions and proposed implementation diagrams.
  • When combining panels, label each source. An analyst's summary, test matrix or handoff mapping is a presenter-created explanation, not a native consolidated product screen.
  • Add a short caption describing the evidence, not a slogan. For example: “Phone update succeeded for the verified contact; the second contact remained unchanged.”
