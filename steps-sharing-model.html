Step 01 of 07

Define who needs access to which data

Describe the required access before choosing profiles, permissions or sharing rules.

Overview

Write down who needs the data, which data they need, what they can do and what they must not do. Use the same four questions for employees, external users, integrations and AI-agent actions.

Separate access to an object, access to its fields and access to individual records. A user may be able to edit Opportunities while remaining unable to read Commission or open another team’s Opportunities.

Illustrative implementation steps

Start with a short access statement

List the main user groups and the work they perform. Specify the record population: their own records, a team’s records, assigned customers or another clear scope. Name sensitive fields that need different access.

Start the master worksheet

Complete the access-requirements rows in the master sharing-model worksheet. Keep business requirements in those rows and add the configuration decisions below them as you work through the journey. The completed example shows how the two parts connect.

Include actions that need their own decision

Consider creating, deleting, exporting, approving and transferring records as well as reading and editing them. Include temporary collaboration and changes of responsibility. A requirement to update a record does not automatically justify every other operation.

Simple examples

Object

Can the sales rep read Opportunities?

Field

Can the sales rep read Commission?

Record

Which Opportunities can the sales rep open?

A clear requirement

Sales reps can read and update assigned Opportunities. They cannot read Commission.

This states the work, the record scope and the field boundary without prescribing a particular configuration.

How Guardian helps

Shield Data Detect helps identify sensitive information that the access requirements need to cover. Scan the selected data using the supplied sensitive-data categories and, where useful, custom patterns for identifiers such as employee IDs. Review the matches with the data owner before deciding which users should be able to read, change or export those values.

Use Security Center Data Classification to record agreed sensitivity levels, compliance categories and data owners on the relevant fields. Bulk classification makes it easier to apply consistent labels across many fields. These labels describe the data; object, field and record permissions still determine access.

For example, if a scan finds personal identifiers in a field currently treated as general business information, add that field to the access requirements. Specify who needs its contents and who must not see them, then use the classification to keep that decision visible during implementation.

Step 02 of 07

Set up profiles, permission sets and groups

Start with an appropriate minimum profile, then add the permissions required for each task.

Overview

Use the profile for a minimal baseline and the settings it must carry. Build additional access through permission sets, and combine them into permission set groups for user personas.

A permission left ungranted in the profile can be granted by a permission set. Inspect the user’s combined permissions, including the effect of group-specific muting.

Salesforce resources: Profiles, permission sets and groups · Muting permission sets

Illustrative implementation steps

1. Set the profile baseline

Choose an appropriate minimum profile. Review login hours, login IP ranges, default apps and record types, and page-layout assignments. Keep baseline permissions narrow enough for the intended users.

2. Add permissions for tasks

Create reusable permission sets for identifiable work, such as maintaining Opportunities or running reports. Specify object actions, field Read/Edit permissions and required system permissions. Include application, Apex-class and custom-permission access when the task needs them.

Salesforce resources: Configure permission sets

3. Assemble groups and apply muting deliberately

Combine the relevant permission sets into a group for a persona. Use muting when that group should omit a permission included in one of its sets. Check direct assignments and other groups for the same grant; muting does not remove their contributions.

4. Configure field access at its source

Object Manager → Fields & Relationships → field → Set Field-Level Security can edit the field permissions on profiles. Those changes belong to the selected profiles. Object Manager can also manage permission-set FLS with the relevant User Management setting enabled.

Use Object Manager → object → Field Access to review which profiles, permission sets and groups grant access to a field. Keep the editing screen and the access-summary screen distinct.

Salesforce resources: Set field-level security in Object Manager · Field Access Summary

5. Review broad grants and UI settings

Review View All Records, Modify All Records, View All Data and Modify All Data separately from View All Fields. Broad record permissions bypass ordinary record sharing; they do not themselves override field-level security.

Removing a field from a page layout does not remove its field permission. Record-type assignment controls which types a user can use when creating or editing; it does not determine whether they can view an existing record.

Salesforce resources: View All and Modify All permissions · Field permissions · Record-type assignment

Simple examples

Field access from a permission set

A profile leaves Commission unreadable. Assign a permission set granting Read on Commission: the user gains field Read permission, while the profile remains unchanged.

An illustrative Sales User group bundles Manage Opportunities and Run Reports permission sets. One assignment supplies both sets’ permissions, subject to muting. These are example names, not prebuilt bundles.

How Guardian helps

Use Security Center’s Who Sees What Explorer and its Compare view to inspect permission differences between users or between configurations such as profiles, permission sets and permission set groups. The comparison includes object and field permissions and system permissions. This helps explain what a proposed permission bundle adds or removes.

For example, compare two sales permission set groups intended for different responsibilities. If both include a broad administrative permission, check whether either persona actually needs it. Use the differences to refine the reusable task permission sets and keep justified exceptions separate. Export the comparison to retain the design evidence, then check the pilot user’s combined access, including assignments outside the proposed group.

Step 03 of 07

Set record defaults and hierarchy access

Decide which records users can access before additional sharing is applied.

Overview

Organization-wide defaults (OWD) establish baseline access to other users’ records. Choose the setting for each object, with separate internal and external defaults where supported.

Decide ownership and parent relationships alongside that baseline. Review hierarchy access explicitly rather than assuming the company organization chart is the right data-access model.

Salesforce resources: Organization-wide defaults · Role hierarchy

Illustrative implementation steps

Choose a baseline for each object

Open Setup → Sharing Settings. Review the choices available for the object and the access intended for the most restricted relevant user.

Salesforce resources: Organization-wide defaults

Check ownership and parent relationships

Identify who owns the records, whether queues are appropriate for supported objects, and what happens on transfer. Inspect master-detail and standard implicit-sharing behavior. An ordinary lookup or an external-ID match is not, by itself, proof of an access grant.

Review Accounts and related Contacts, Opportunities and Cases together. Test the parent and child access created by the selected model.

Salesforce resources: Platform Sharing Architecture

Design hierarchy access deliberately

Place users in roles based on the visibility they need. On custom objects, review Grant Access Using Hierarchies. Turning it off removes that access route; other applicable grants can still provide access. Hierarchy does not supply missing object or field permissions.

Salesforce resources: Role hierarchy

Plan the change before applying it

Check existing sharing rules, integrations and automation before tightening a baseline. Test with representative data and user roles. Allow for sharing recalculation and inspect the resulting access before proceeding with the next migration batch.

Simple examples

Private does not mean “owner only”

A custom Review object is Private and hierarchy access is disabled. A reviewer receives an explicit sharing grant for a record. The reviewer can still read it if their object permissions allow; disabling hierarchy did not remove that separate grant.

Salesforce resources: Role hierarchy

Record access does not supply field access

A manager receives access to an Opportunity through the role hierarchy. If no profile or permission-set grant permits that manager to read Commission, hierarchy access does not make the field readable.

Salesforce resources: Field permissions

How Guardian helps

Who Sees What Explorer’s Records lens in Security Center helps explain the access produced by the current sharing configuration. Select a representative record and inspect which users have Read, Edit or Delete access and the reasons reported, such as a profile, permission set, sharing rule or role hierarchy.

For example, investigate why a manager can read a record on a Private object. If hierarchy access is the reason, compare that result with the intended management visibility. If another grant supplies access, changing the hierarchy alone will not remove it. After changing OWD or hierarchy settings in a test environment, repeat the inspection and the actual user-access checks; the Explorer view is evidence to investigate, not a simulation of an unapplied change.

Salesforce resources: Who Sees What Explorer

Step 04 of 07

Share records with the people who need them

Choose a sharing mechanism that follows the business relationship and can be maintained.

Overview

Give each additional record grant a clear reason: team responsibility, a defined record category, a named collaboration or another business relationship.

Sharing rules open access. They cannot take away access already provided by another route. Keep permission set groups, which bundle capabilities, distinct from public groups used as sharing recipients.

Salesforce resources: Sharing rules

Illustrative implementation steps

Match the mechanism to the requirement

Select the mechanism for the relationship
RequirementMechanism to consider
Visibility up the management data hierarchyRole hierarchy
A predictable set of owners or record valuesOwner-based or criteria-based sharing rule
Named colleagues collaborating on a supported recordAccount, Opportunity or Case team
Sales coverage organized by territorySales Territories and its sharing model
A specific one-off collaborationManual sharing
A relationship that standard mechanisms cannot expressProgrammatic sharing with explicit grant and removal logic

Salesforce resources: Platform Sharing Architecture

Configure the recipients and access level

For a sharing rule, identify the record population, recipient role or group, and Read Only or Read/Write level. Verify group membership and any included subordinates. Give the rule a description explaining the business requirement.

Use supported teams for record-specific collaboration. Check related Account access and the actual team access level, rather than treating a team-role label as a permission grant.

Salesforce resources: Sharing rules · Opportunity Teams

Define what removes the access

Document the event that ends the grant: a changed record attribute, removed group or team membership, completed assignment or approved expiry. After removal, check whether another access route still applies.

For manual shares, inspect Keep manual shares when transferring records and test owner transfer. Current Salesforce behavior depends on this setting and the transfer scenario.

Salesforce resources: Manual sharing considerations

Keep custom sharing maintainable

When code creates shares, implement removal and repair as well as creation. Test relationship changes, ownership changes, duplicate requests and bulk updates. Review the relevant share object and supported sharing reasons before choosing an implementation.

Simple examples

Criteria-based sharing

A custom Project object is Private. Share Projects with Region = East to an East Support public group as Read Only. Members gain a record-sharing route to those Projects; object and field permissions still apply.

Illustrative configuration using standard criteria-based sharing.

Salesforce resources: Sharing rules

Opportunity team

A specialist needs to work on one Opportunity. Add the specialist to that Opportunity’s team with the appropriate access. When the assignment ends, remove the team membership and check for any remaining access through other routes.

Salesforce resources: Opportunity Teams

Two different kinds of group

A permission set group can bundle the permissions to read Projects. An East Support public group can be the recipient of a rule sharing particular Project records. Both decisions may be needed.

How Guardian helps

Shield Event Monitoring helps review how newly shared data is used. Set up the Event Monitoring Analytics app and start with its Reports, Report Downloads and API dashboards. These show report use, report exports and API activity, helping you focus a review on particular users, applications and periods after a sharing change.

For example, a team receives access to a new record population and subsequently starts downloading reports it did not previously use. Inspect the activity with the team’s business purpose in mind and check the sharing and export permissions involved. Activity can identify a grant worth reviewing; absence of activity does not establish that the access is unnecessary.

Shield Field Audit Trail can retain changes to supported fields that drive criteria-based sharing, such as a custom Region field. Enable tracking before the changes occur and configure retention. If a record moves from East to West, the field history can help explain the change in its sharing criteria. This records field changes; it does not preserve a complete history of sharing-rule definitions or everyone’s past access.

Salesforce resources: Event Monitoring prebuilt dashboards · Field Audit Trail

Step 05 of 07

Restrict sensitive access and secure other access paths

Review restriction rules, external and guest access, and the context in which automation runs.

Overview

Check whether the combined grants expose more data than intended. Use restriction rules for suitable requirements on supported objects, and examine external access and custom execution paths separately.

Scoping rules help users focus on records. They do not withdraw access to other records the user is authorized to see.

Salesforce resources: Restriction rules · Scoping rules

Illustrative implementation steps

Apply restriction rules to a specific requirement

On a supported object, define which users the rule applies to and which records remain accessible to them. Make user criteria unambiguous. Do not create overlapping restriction/scoping rules for the same object and user expecting them to combine.

Test the actual access paths. System-mode code and specified broad record permissions bypass restriction rules. A parent restriction does not automatically secure child objects, and activity views have documented limitations.

Salesforce resources: Restriction rules · Restriction-rule considerations

Secure authenticated external-user access

Decide whether a customer should see only their own records or their organization’s records. Check the external-user type and supported sharing mechanism. Where sharing sets fit, map the user’s Contact or Account to the matching relationship on the target record.

Test one customer’s access to another customer’s record, including direct URLs, files and the services used by the site.

Salesforce resources: Sharing sets for external users

Secure guest-user access

Review each site anonymously. Guest record access is private; deliberate read-only access can be provided through guest-user sharing rules. Manual and Apex managed sharing are not alternatives for granting guest access.

Keep rule criteria narrow and review guest object and field permissions. A guest sharing rule exposes matching records to unauthenticated visitors. Inspect public files and any custom service that returns data.

Salesforce resources: Guest-user record access

Check Apex, Flow, integrations and agent actions

Record the running identity, launch method and execution context. In Apex, check the class/API version, sharing declaration and database-operation access mode. with sharing addresses record sharing; object and field checks also need to be enforced through the appropriate operation mode or explicit controls.

Inspect Flow’s run context and callers. A flow or agent action that invokes elevated automation needs an authorization review of that path. Use narrowly scoped integration identities and permissions instead of assigning System Administrator to make an integration work.

Salesforce resources: Secure Apex classes · Flow run context

Review other ways sensitive information can appear

Include reports, dashboard running users, files and public links in the access review. Check formulas and custom components that expose derived information: a formula can reveal a value based on a field the user cannot read directly.

Salesforce resources: Field permissions

Simple examples

Restriction rule: only Tasks the user owns

For users with a selected profile, keep only otherwise accessible Tasks owned by the current user. Salesforce’s documented example selects the profile in user criteria and compares Task.Owner:User.Id with $User.Id in record criteria.

This filters existing access; it does not grant new access. Apply the documented bypass and activity-view considerations.

Salesforce resources: Salesforce restriction-rule examples

Scoping rule: focus the working list

Focus a sales rep’s Account list on Accounts they own, using the scoped view. Other Accounts already authorized by the sharing model remain accessible. This is a working-view filter.

Salesforce resources: Scoping rules

External sharing: customer account

A sharing set maps a site user’s Account to the Account on a Case. Matching Cases become accessible at the configured level. This is appropriate only if the intended requirement is account-wide access, rather than access limited to the individual contact.

Salesforce resources: Sharing sets for external users

How Guardian helps

Shield Transaction Security Policies add controls to supported activities involving data a user can already access. For example, a ReportEvent policy can block a report export that exceeds an agreed row threshold, or require MFA on a supported UI action. An ApiEvent policy can block matching API activity using conditions such as the application, queried objects or rows processed.

Use the TSP Accelerator from Salesforce Labs as a starting point. Review a policy’s conditions, supported actions and setup requirements, then adjust it to the intended workload. Test permitted and prohibited activity in a sandbox, including integrations that legitimately process large volumes.

Keep the scope of each policy explicit. A report policy does not cover every API or custom-code route. Continue to enforce object permissions, field permissions, record sharing and the appropriate Apex or Flow execution context on those paths.

Salesforce resources: Transaction Security conditions and actions · TSP Accelerator from Salesforce Labs

Step 06 of 07

Test access and migrate safely

Check intended access and intended denials, then move users in controlled batches.

Overview

Test with representative non-admin users. Confirm that required work succeeds and that prohibited records, fields and actions remain inaccessible.

Migrating permissions from a profile to a permission set does not by itself reduce access. Review which grants are still justified before assigning the replacement.

Illustrative implementation steps

Use a short access-check table

Does access match the requirement?
CheckExpectedActual
Sales rep opens an assigned OpportunityAllowed
Sales rep reads CommissionDenied
 

Repeat relevant checks in the UI, reports, APIs and automation actually used. Add team or ownership changes as further rows when they apply.

Find the source of an unexpected grant

Open Setup → Users → user → View Summary. Use Access Granted By to trace a permission to its profile, permission set or group. Use Object Manager → object → Field Access for a field-focused review.

Inspect record-sharing reasons as well. A permission summary is not a complete record-access test. In particular, UserRecordAccess does not account for blocking by restriction rules.

Salesforce resources: User Access Summary · Field Access Summary · Restriction-rule considerations

Prepare the replacement permissions

The User Access and Permissions Assistant (UAPA) can convert a profile to an editable permission set. Its documented conversion excludes record types and tab access. Review the output against the required work instead of treating conversion as a complete migration.

Salesforce resources: Profile conversion with UAPA

Pilot, then expand

Preserve the existing configuration and assignments. Prepare the minimum-profile settings and replacement permission sets/groups, then pilot one persona in a suitable test environment. Check applications, reports, integrations, automation and managed-package functions used by that persona.

Remove obsolete grants during the pilot and rerun the checks. Prepare rollback instructions before production rollout. Migrate in manageable batches, allowing for group/sharing recalculation and investigation of unexpected results.

Simple examples

Trace an unexpected field grant

A sales rep can read Commission despite the profile leaving it ungranted. Inspect the sources of field access and find an old direct permission set. Remove the unintended grant at its source, then repeat the field-access check.

Salesforce resources: User Access Summary

Test a move as well as a new assignment

A user moves from East Support to West Support. Test that the user gains the required West access and loses the East access that is no longer justified. Include old public-group memberships, direct assignments and exceptional shares in the review.

How Guardian helps

Use Data Mask, within Data Mask & Seed, to protect sensitive values in the sandbox used for the sharing-model pilot. Configure replacement, scrambling or deletion for the selected fields before opening the environment to testers. Masking changes the stored sandbox values; it does not alter production data or simply hide a value on screen.

Prepare the masking scope around the access scenarios. If a sharing or restriction rule depends on a field value, retain or recreate representative test values for that condition. Keep the required record relationships and test both allowed and denied access. Confirm that masking completed and inspect the records before starting the pilot.

When a test exposes unexpected access, use Who Sees What Explorer to investigate the user’s object, field or record-access reasons. Correct the grant at its source and repeat the actual test. This combines a protected test dataset with an explanation of the access being exercised.

Salesforce resources: Data Mask mechanics · Who Sees What Explorer

Step 07 of 07

Maintain access as users and data change

Keep assignments, sharing relationships and exceptions aligned with current responsibilities.

Overview

Define how access is granted, changed and removed when people join, move teams or leave. Assign owners to permission groups, public groups, sharing rules and exceptional access.

Recheck affected access when fields, relationships, applications or automation change. Keep the focus on unexplained grants and requirements that no longer hold.

Illustrative implementation steps

Automate explicit grant and removal actions

Use User Access Policies to grant or revoke supported assignments when qualifying user records are created or updated. Define the criteria, actions and policy order. Where multiple active policies match, the lowest order applies.

Include removal of old assignments in the mover/leaver design. Do not assume that a user ceasing to match a previous grant condition automatically supplies the revocation behavior you need. Inspect policy results after a controlled user change.

Salesforce resources: Automated User Access Policies

Review exceptions and remaining access

Record a reason and review date for exceptional grants. Revisit broad permissions, direct permission-set assignments, team memberships, public groups and manually maintained shares. Confirm that an exception still supports current work.

Recheck after configuration changes

When a field is added, review its permissions and any formulas that expose it. When ownership, roles or relationships change, test the affected record populations. Recheck integration and agent actions after changes to their identity, code or Flow context.

Track a small set of useful findings: unexpected grants, expired exceptions, obsolete assignments after a move and failed access checks. Record the action taken and the resulting access.

Simple examples

User Access Policy: remove the old assignment

A user’s Department changes from Sales to Support. A matching policy can explicitly grant the Support permission set group and revoke the Sales group. Check remaining direct assignments and other access routes separately.

Salesforce resources: Automated User Access Policies

Permission drift: a new broad grant

A user receives Modify All Data through a newly assigned permission set. A configured Security Insights alert identifies the change. The reviewer checks the business reason, removes an unintended grant and confirms the user’s resulting access.

Salesforce resources: Security Insights alerts

How Guardian helps

Use Security Center Security Insights alerts to monitor high-risk permission drift after the sharing model is established. For example, configure an alert for Modify All Data being assigned to a user. Also review the alert rule for high-risk permissions assigned to profiles, permission sets or permission set groups.

Subscribe the reviewers responsible for access changes. When an alert identifies a new grant, inspect the affected user and the configuration supplying it. Compare the assignment with the approved responsibilities, remove an unintended grant at its source and recheck the user’s resulting access. Test alert delivery with a controlled assignment and check its timing against the analysis schedule.

Use the Security Insights Progress Report to compare successive analyses and follow up on regressions. These alerts support review; they do not themselves block a permission assignment. Continue checking record-sharing rules, group membership and exceptional shares alongside the supported permission alerts.

Salesforce resources: Security Insights alerts · Security Insights reports and scheduled analysis
